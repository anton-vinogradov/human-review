# Как формировать навык Human Review

Эти правила описывают, как модель превращает замечания пользователя в критерии проверки кода. Модель опирается на обсуждение и на правки, которые пользователь уже принял. Новую формулировку она предлагает пользователю. Если пользователь её принимает, модель включает критерий в документ. В дальнейшем модель использует принятые критерии для составления инструкций навыка. Все тексты модель пишет по human-writing, включая критерии, сам навык и сообщения пользователю.

## Какие критерии нужны

Критерий нужен, когда он объясняет важное для пользователя различие между двумя допустимыми решениями. Если выбор уже объясняет другой критерий или обычная проверка кода стабильно приводит к тому же выводу, модель считает отдельное правило избыточным.

## Как модель выясняет цель

Модель начинает с замечания пользователя или с правила, которое уже есть в human-review. Она выясняет, какой результат стоит за замечанием и почему он важен. Если у принятой правки есть несколько объяснений и от выбора зависит смысл критерия, модель показывает различие и задаёт вопрос пользователю.

## Как модель формулирует критерий

Модель описывает, какое свойство изменения имеет значение, как его распознать и почему оно влияет на выбор. Она указывает условия, при которых её вывод изменится. Формулировка должна подходить и для другого решения, которое достигает той же цели.

## Как модель находит место для критерия

Модель ищет ближайший по смыслу критерий. Если он уже объясняет тот же выбор, его достаточно. Если новый случай уточняет границу его применения, модель предлагает дополнить формулировку. Близкие идеи она располагает рядом и объединяет, пока понятно, почему два похожих изменения заслуживают разной оценки.

## Как должен читаться документ

В обсуждении участвуют только пользователь и модель. Для каждого критерия модель описывает, что она проверяет и как поступает в зависимости от результата. Когда критерий определяет выбор, в тексте прямо названо действие модели. Если выбор зависит от решения пользователя, модель объясняет причину и задаёт вопрос. Пользователь сам решает, отвечать ли на вопрос и принимать ли предложение. Например, модель исправляет подтверждённый дефект в пределах задачи сама, а попутное улучшение включает в работу, только если пользователь решит расширить её границы.

Заголовок называет свойство, по которому модель оценивает изменение. Сам критерий читается как связный рассказ в настоящем времени. Каждый абзац отвечает на один вопрос и начинается с главного. Модель называет, что проверяет, затем объясняет, как результат проверки влияет на её действие. Когда выбор требует пояснения, модель показывает, что от него зависит. Свойства кода, тестов, документации и журналов она описывает прямо.

Модель раскрывает смысл терминов при первом употреблении. Иногда достаточно показать действие и его результат. Если несколько терминов приходится использовать вместе, модель даёт перед ними короткую легенду с их значениями. Точность нужна и для обычных слов. Если в тексте что-то названо «согласованным», должно быть понятно, о чём договорились и откуда это известно.

После переработки модель сверяет текст с принятой редакцией и проверяет, сохранились ли требования, их причины и исключения. Затем она перечитывает весь документ по human-writing с позиции первого знакомства с навыком. Если выбор модели можно понять лишь из примера, в саму формулировку нужно перенести условие, от которого этот выбор зависит.

Каждая языковая версия навыка заканчивается благодарностью модели за предстоящую работу. Последняя строка русской версии — «Заранее спасибо за внимательную проверку и исправления!». Английская версия завершается строкой «Thank you in advance for the careful review and fixes!».

## Как подготовить навык к установке

Модель выпускает английский `SKILL.md` как точку входа и русский `SKILL.ru.md` с теми же инструкциями. Имя навыка в метаданных остаётся `human-review`, чтобы существующие установки и вызовы `$human-review` продолжали работать. В обеих версиях README модель показывает, как установить навык в используемом агенте, проверить его доступность и запустить ревью. Команды для Codex явно помечает как команды для Codex.

Для автообновления нужен отдельный Git-клон официального репозитория на ветке `main`. Для обновления в инструкции указаны Git, Python 3.9 или новее, доступ к сети и право записи в каталог установки. Для чата без установки достаточно приложить файл навыка, изменения и исходный код. Если у пользователя уже есть копия с правками, инструкция объясняет, как сохранить её вне каталогов навыков перед переходом на Git-клон. [Установка и переход с существующей копии](https://github.com/anton-vinogradov/human-review/blob/main/README.ru.md)

## Как обновляется установленная версия

Новая установка начинает работу с выключенным автообновлением. Пользователь может один раз включить его для этой установки командой с `--enable` и позже отключить с `--disable`. README объясняет, что согласие распространяется на будущие изменения из `main`, включая саму программу обновления. Такое согласие относится только к установленному навыку. Права на изменение проверяемого проекта определяет запрос пользователя на ревью.

В обеих версиях навыка модель сохраняет инструкцию перед ревью запускать `scripts/update.py` по пути установленного навыка. Скрипт проверяет наличие согласия и обращается к источнику не чаще раза в 24 часа, включая неудачные попытки. Для отдельной ручной проверки `--force` снимает только ограничение по времени. После результата `updated` модель перечитывает инструкции и применяет их в текущем ревью.

Обновление затрагивает только чистый клон нужного репозитория на ветке `main` и применяется, если новая версия продолжает установленную историю. При локальных правках, дополнительных файлах или расхождении истории скрипт сохраняет установку. Если проверку пропустили, не хватает разрешений, инструментов или доступа к сети, модель проводит ревью по доступной установленной версии. [Скрипт обновления](https://github.com/anton-vinogradov/human-review/blob/main/scripts/update.py)

## Что проверить перед публикацией

Модель сверяет обе языковые версии с принятыми критериями, включая исключения, действия при сбое и решения, которые остаются за пользователем. Она проверяет, что последняя строка каждой версии навыка совпадает с благодарностью на соответствующем языке. Затем проверяет метаданные навыка, ссылки, пути и команды в обеих версиях README. Из инструкции должно быть понятно, как получить первую установку и как существующая установка получит эту редакцию после публикации в `main`.

Из корня репозитория модель запускает `python3 -B -m unittest discover -s tests -v`. Тесты работают на временных Git-репозиториях без доступа к сети. Они проверяют смену настройки, обновление файлов навыка, сохранение локальных правок, сбои сети и защиту проверяемого проекта. Если меняется способ установки или обновления, модель дополнительно проходит изменённые шаги в отдельной тестовой установке. [Тесты обновления](https://github.com/anton-vinogradov/human-review/blob/main/tests/test_update.py)
